# Mind-Robot 设计文档

目标版本：Minecraft **1.7.10** / Forge **10.13.4.1614**（MCP stable/12），Java 8 字节码（Jabel 现代语法）。
本文只记录**已确认**的规则与由规则推导出的技术决策；未确认项统一列在第 6 节。

---

## 1. 玩法规则（已确认）

| 编号 | 规则 |
|---|---|
| R1 | 机器人是**独立实体**，有自己的位置、碰撞箱与生命值。 |
| R2 | 玩家戴上**遥控头盔**（头部位护甲）后，打开**转轮面板**，选择「操作机器人」进入驾驶。 |
| R3 | 转轮面板是**通用交互面板**，后续功能都挂同一个面板，不另做新界面。 |
| R4 | 驾驶期间，**摄像机与操作全部作用于机器人**。 |
| R5 | 玩家本体**留在原地的进入点**，不跟随移动。 |
| R6 | 本体仍受世界影响：怪物能攻击、饥饿会掉、跌落会受伤。**驾驶期间你背后是敞开的**。 |
| R7 | 本体血量归零（任何原因，含饥饿）→ **立即中断连接**。 |
| R8 | 机器人被摧毁 → **强制退出，玩家本体存活**。 |
| R9 | 控制距离**不设上限**。 |
| R10 | 驾驶期间**玩家无法操作自己的物品栏**，头盔也**摘不下来**（护甲槽锁定）。 |
| R11 | **退出通道**：机器人视角里同样能打开转轮面板，从面板选择退出。 |
| R12 | 转轮面板**双上下文**：戴头盔的玩家看到「操作机器人」；驾驶中的玩家看到「退出」与后续功能项。 |
| R13 | 头盔与机器人通过**频道芯片**配对：两边芯片的频道号完全相同即可配对；一台机器人同一时刻只服务一个驾驶员。 |
| R14 | 机器人来源：在**机器人装配台**方块里，用**两条手臂 + 两条腿 + 内置核心 + 摄像头**组装，完成后放出实体。 |
| R15 | 机器人能力面：移动、挖掘方块、攻击、交互/使用物品。 |
| R16 | 机器人有**独立的机体结构耐久**，远高于玩家生命值；上限 = 身上所有零件耐久之和；**不可恢复**；归零即机体损毁。 |
| R17 | 结构耐久**不是** `EntityLivingBase` 的生命值：不能被治疗、不参与原版死亡流程、不能被第三方模组当作生命值读取或榨取。 |
| R18 | 机器人会被怪物**主动攻击**（与玩家同等对待）。 |
| R19 | 免疫水下窒息与摔落伤害；`inWall`（卡在方块里的挤压/窒息）伤害 **×4**。 |
| R20 | 机体损毁后按 R8 强制退出驾驶，玩家本体存活。 |
| R21 | 配对靠**频道芯片**：芯片由玩家设置频道号（数字），装进头盔；机器人同样装芯片。两边号码完全相同即可建立控制关系。 |
| R22 | 频道分**公共**与**私人**，**由芯片决定**：公共频道用数字频道号识别，任何同号者都能连；私人频道用**自定义名称 + 密码**识别，两项都对上才能连。所有者 UUID 不再参与判定。 |
| R23 | 驾驶期间机器人所在区块**强制保持加载**（服务器强制 ticket），避免区块卸载把远处的机器人"睡掉"。 |
| R24 | 机器人所在区块**卸载不判定为损毁**：连接保持，按最后已知位置把区块重新拉回来，实体加载后继续驾驶。 |
| R25 | 频道被占用时**先到先得**：后来者收到"频道被占用"，既不抢占也不排队。 |
| R26 | 机器人没有芯片或频道未设置时**不可连接**。 |
| R27 | 定位由**机器人自己上报**：机器人周期性把自己的位置写进世界级登记表；头盔里那份只是**展示镜像**，不作为唤醒依据。断开时机器人再补报一次。重连时服务端按登记表里该频道的记录把区块唤醒，加载到实体后再走校验并接入。 |
| R28 | 检索与唤醒分开：**公共频道不唤醒**——只在当前已加载的机器人里检索，命中才判占用；**私人频道才唤醒**——名称与密码对上后，从登记表取出该机器人坐标并强制加载区块，60 tick 内重试接入。私人凭据即唤醒授权，公共频道不允许任何人凭频道号拉区块。 |
| R29 | 头盔是**脑机头盔 MKI**，后续有升级版（MKII、MKIII…）。代数之间的主要差异是**驾驶时的画面噪点**：代数越高画面越干净，MKI 有明显雪花与偶发干扰，MKIII 近乎无噪点。 |
| R30 | 每个代数是**同一种物品的不同元数据档位**（不是多个独立物品），这样升级链与配方可以共用一套，也不会污染创造模式物品栏。 |
| R31 | 脑机头盔在**合成台**合成（各代各一条配方）。 |
| R32 | 连接芯片的安装方式：**手持脑机头盔潜行右键打开容器**，其中只有**一个可放置的槽位**、只接受连接芯片（其余是标准玩家背包格，否则没法把芯片移进去）；放入即把频道快照写进头盔，芯片实体存进头盔 NBT 可再取出，**取走即清空频道**。旧的"捧芯片潜行点头盔"路径废弃。 |
| R33 | 摄像头槽可替换为**热成像摄像头**：装配出的机器人在被驾驶时，视角获得**夜视**。 |
| R34 | 装配台每个槽位有类型约束（左臂 / 右臂 / 左腿 / 右腿 / 核心 / 摄像头），塞错位置不接受。 |
| R35 | **右键机器人实体**打开它的物品容器。布局：第一行 9 格=**驾驶时玩家操作的工具栏**；6×9=54 格**背包**；1 个**芯片槽**；1 个**电池箱槽**。 |
| R36 | 机器人**自动拾取**物品，拾取物直接进入背包（背包满了才进工具栏），**绝不进入芯片槽与电池槽**。 |
| R37 | 槽位强隔离：芯片槽只收连接芯片；电池槽只收电池；工具栏与背包**拒收**芯片与电池。这是为了杜绝"矿物被自动塞进电池槽"这类串位。 |
| R38 | **GT5U（gregtech）是本模组的前置**；电池槽的接受判定与 GT 机器电池槽一致（IC2 的 `IElectricItem`）。 |

R6/R7 是核心张力：遥控本身不强，代价是身体无人看守。任何"顺手让本体无敌"的实现都违背设计意图。

## 2. 技术决策

### D1 · 摄像机必须由客户端接管
`Minecraft.renderViewEntity` 的声明类型是 `EntityLivingBase`（`net/minecraft/client/Minecraft.java:212`），不是 `Entity`。

推论：**机器人实体必须继承 `EntityLivingBase`**，否则不能当视角载体。

- 连接建立后客户端把 `mc.renderViewEntity` 指向机器人；断开时归还 `mc.thePlayer`。
- 必须同时屏蔽本体第一人称渲染（手部、视角模型），否则画面会叠着本体的视角。
- 服务端不参与视角，只负责告诉客户端"你现在连的是哪个实体"。

### D2 · 输入权威在服务端
客户端只发**输入意图**（前后/左右/朝向/跳跃/潜行/攻击/使用），服务端按 tick 校验并驱动机器人。客户端不允许直接改坐标，否则飞行、加速、穿墙都能伪造。

### D3 · 本体冻结的正确边界
"屏蔽对身体的操作" ≠ "免疫"：

| 类别 | 驾驶期间 |
|---|---|
| 玩家输入（移动/转向/跳跃/攻击/使用/开背包） | 丢弃，不作用于本体 |
| 本体位置 | 每 tick 归位到进入点（防活塞、水流、爆炸推动） |
| 世界伤害（怪、摔落、火、岩浆） | **照常生效** |
| 饥饿与自然回血 | 照常（R6），血量到 0 走 R7 |
| 护甲槽 | 锁定，头盔不可摘下（R10） |

### D4 · 断线只有一个入口
所有结束路径（本体死亡、机器人死亡、玩家在转轮面板点退出、玩家断线、维度切换、服务器停止）都走 `RobotLinkManager.disconnect(player, reason)`：解绑 → 归还摄像机 → 恢复输入 → 清空 anchor。分散处理会留下"幽灵连接"。

### D5 · 频道数据模型（芯片决定频道类型）
**频道类型由芯片决定**：装进头盔的是哪种芯片，这次连接就按哪种方式检索；机器人上的数据只是被比对的对象。

| 载体 | 公共频道 | 私人频道 |
|---|---|---|
| 芯片 NBT | `mode=PUBLIC` + `channel`（int 0–9999） | `mode=PRIVATE` + `name`（自定义名称）+ `passwordHash` |
| 头盔 NBT（安装时的快照） | 同上 | 同上 |
| 机器人 NBT / 登记表行 | 同上 | 同上 |

- **密码明文存储**：芯片、头盔、登记表里都存原始字符串，服主可以直接编辑 `<world>/mindrobot/robots.json` 把忘记的密码改回来。代价是任何能读存档的人都能看到密码——这是刻意换取的"可救回"，不做散列。**登记表用 JSON 而不是 NBT `.dat`**，就是为了让服主不用 NBT 编辑器、记事本就能改。
- 名称 1–32 字符（允许中文，两端空白会被裁掉），密码 1–64 字符（**不裁**，大小写敏感）；名称或密码为空视为"未配置"（R26 不可连接）。
- 私人频道检索顺序：**先看已加载实体**（凭据匹配就直接接入，不动区块），只有未加载时才查登记表并唤醒；拒绝提示区分"名称不存在"和"密码不对"，且**永不回显密码**。
- **所有者 UUID 语义废弃**（R22 改写）：私人频道的门槛就是"知道名字和密码"，谁能对上谁就能用；芯片被复制/交易后新持有者自然可用，这符合"遥控设备"的直觉。
- **不做任何旧版本兼容**：这个模组从未发布、也从未生成过机器人或做过真实存档实验，因此不存在需要迁移的历史数据。旧格式 NBT（旧 `channel + owner`、早期只存在实体 NBT 里的频道）一律视为"未配置"直接忽略，**不写迁移分支、不写物化逻辑**。这条是硬约束：任何"为了可能存在的旧数据"而加的兼容代码都不加。

判定顺序（服务端唯一入口）：
1. 头盔没有芯片或字段不全 → 拒绝。
2. **公共**：在**已加载**的同号机器人里找最近的；**私人**：在登记表里按"名称相同 + 密码散列相同"找。
3. 命中后判占用：同一台机器人同一时刻只有一个驾驶员（R13/R25），已被占用则拒绝。
4. 公共频道命中即接入；私人频道命中后还要唤醒其坐标区块（R28）。

### D10 · 强制加载走 ForgeChunkManager
已核对 1.7.10 的 API 存在：`ForgeChunkManager.requestTicket(Object mod, World world, Type type)`、`forceChunk(Ticket, ChunkCoordIntPair)`、`unforceChunk(...)`、`releaseTicket(Ticket)`。

- 连接建立时申请一张 `Type.NORMAL` ticket；机器人每跨区块就 `forceChunk` 新区块 + `unforceChunk` 旧区块（ticket 位置跟着走，不是无限扩大加载范围）。
- 断开（`RobotLinkManager.disconnect` 的任意原因）必须 `releaseTicket`，否则 ticket 泄漏会永久占用区块加载。
- 机器人跨维度时先释放再在新世界重建 ticket。

### D6 · 转轮面板是纯客户端自绘 + 服务端选项裁剪
菜单项由服务端按上下文下发（是否戴头盔、是否在驾驶），客户端只负责画轮盘与命中检测。新增功能 = 服务端多一条选项 + 客户端多一个扇区，不动渲染框架。

### D7 · 结构耐久必须与生命值物理隔离
摄像机要求实体是 `EntityLivingBase`（D1），但如果直接拿它的 `health` 当耐久，会同时踩两个坑：

1. **变成材料源**：血魔法一类模组通过击杀/献祭把生物生命值换成资源。机器人一旦有可被击杀的 health，玩家就能刷它。
2. **崩溃高发**：第三方模组会读 `getMaxHealth()` / `getHealth()` 做伤害计算、状态条、AI 判定。一个"血量几万"的 `EntityLivingBase` 会让这些逻辑溢出、除零，或在它身上挂装备/掉落表时炸掉。

实现方式：

| 层 | 做法 |
|---|---|
| 生命值 | 伪装层。`applyEntityAttributes()` 注册 `maxHealth` 与 `movementSpeed`（防 NPE），`setHealth` 覆写成空操作，构造函数里用 `super.setHealth()` 写一次初值，于是对外恒定读到 20/20、永不进入死亡流程。**注意：`getHealth()` 与 `getMaxHealth()` 在 1.7.10 是 `final`（`EntityLivingBase.java:807` / `:1289`），无法覆写**；`setEntityHealth` 在 1.7.10 也不存在。 |
| 伤害入口 | 覆写 `attackEntityFrom` 且**不调 super**，转进自己的管线。这样 `LivingAttackEvent` / `LivingHurtEvent` / `LivingDeathEvent` 都不会为它触发，第三方伤害修正与击杀回调完全看不到它。`onDeath` 也重定向到 `destroyRobot()` 作为兜底。 |
| 真耐久 | 独立字段 `structuralIntegrity`，NBT 持久化，只由自己的破坏路径扣减，没有任何恢复路径。 |
| 销毁 | 归零走 `destroyRobot()`：播效果 → 通知连接管理器断开 → `setDead()`，**不经过原版死亡流程**。 |
| 兼容 | 公开 `IRobotCore` 接口（`getStructuralIntegrity` / `getMaxStructuralIntegrity` / `applyStructuralDamage` / `isRobot`），愿意适配的模组显式对接。 |

附带收益：实体只继承 `EntityLivingBase` 而不继承 `EntityLiving`，没有装备栏、掉落表和 AI 任务表，对第三方模组的暴露面更小。

### D8 · 仇恨：必须注入"目标 + 攻击"两条 AI，再加周期扫描
1.7.10 的僵尸/骷髅只注册了针对 `EntityPlayer` 的目标 AI（`EntityZombie.java:75`：`new EntityAINearestAttackableTarget(this, EntityPlayer.class, 0, true)`），机器人不是玩家，天然不会被主动攻击。

**只注入目标 AI 是不够的**：`EntityAIAttackOnCollide` 有 `classTarget` 字段，`shouldExecute()` 里会检查 `!classTarget.isAssignableFrom(target.getClass())`（`EntityAIAttackOnCollide.java:61`）。僵尸的攻击任务是 `EntityAIAttackOnCollide(this, EntityPlayer.class, ...)`，所以即使我们强行把它的 target 设成机器人，攻击任务也会判定类不匹配而拒绝执行——怪只会站着发呆，不会追也不会打。

因此要注入**两条**：

| 注入对象 | 内容 | 缺失后果 |
|---|---|---|
| `mob.targetTasks` | `new EntityAINearestAttackableTarget(mob, EntityRobot.class, 0, true)` | 怪根本不锁定机器人 |
| `mob.tasks` | `new EntityAIAttackOnCollide(mob, EntityRobot.class, speed, false)` | 锁定了也不打、不追（classTarget 不匹配） |

执行方式：
- `EntityJoinWorldEvent`（服务端）时为每个 `EntityCreature` 注入两条任务，注入前去重（避免重复叠加导致 AI 抖动与内存膨胀）；只对 `EntityMob` 注入，别给牛羊塞。
- 机器人进入世界时，对已加载范围内的怪补注入一次（它们早就在世界里，不会触发 join 事件）。
- 追加**周期仇恨扫描**（节流执行，例如每 20 tick）：对已加载的 `EntityCreature`，若 `getAttackTarget() == null` 且机器人在其追踪范围内且可见，则 `setAttackTarget(robot)`。这条覆盖"没有注册 vanilla 目标 AI、但攻击逻辑读 `getAttackTarget()`"的第三方怪。
- 机器人攻击某只怪后，原版 `EntityAIHurtByTarget` 会接管反击。

**为什么不干脆把机器人伪装成玩家**：`EntityPlayer` 子体会引出比解决的问题更多的崩溃点。
- 服务端模组普遍 `entity instanceof EntityPlayerMP` 后直接取 `playerNetServerHandler` / `getServerForPlayer()` / 权限系统，我们拿不出现实 handler → NPE。
- 只继承 `EntityPlayer` 时服务端 `instanceof EntityPlayerMP` 为假，客户端与服务端认的"玩家"不是同一个类型，判定分裂。
- 玩家身份会触发死亡掉落、经验、计分板、Boss 血条、灵魂绑定/吸血类模组的目标扫描，与 R17「不能被当作生命值榨取」直接冲突。
- 结论：伪装成玩家的覆盖率是 100%，但崩溃面也是 100%。不采用。

**诚实说明覆盖率**：走 vanilla AI 的模组怪（1.7.10 绝大多数）全覆盖；完全自研 AI、不读 `getAttackTarget()`、不经过 `EntityAIAttackOnCollide` 的特殊 Boss 覆盖不到，需要按模组单独适配。

### D9 · 伤害策略表

| `DamageSource` | 系数 | 说明 |
|---|---|---|
| `drown` | 0 | 免疫水下窒息 |
| `fall` | 0 | 免疫摔落 |
| `inWall` | ×4 | 卡在方块里的挤压/窒息，翻四倍 |
| `outOfWorld` | 直接销毁 | 掉虚空就机毁，不留幽灵连接 |
| 其它 | ×1 | 普通结构伤害 |

注意：1.7.10 的 `DamageSource` 只有 `inWall`/`drown`/`fall`/`outOfWorld`/`generic`/`magic`/`anvil`/`fallingBlock`，**没有 `cramming`**。"生物互相挤压造成伤害"是 1.8 之后才有的机制；要实现那种"被一群怪挤爆"的规则得自己写（重叠实体数持续超过阈值 N tick 后扣耐久），属于新增机制，见第 6 节 Q5。

### D12 · 头盔代数与画面噪点（R29/R30）
**物品形态**：单个 `ItemBrainHelmet`，`setHasSubtypes(true)`，metadata = 代数（0=MKI、1=MKII、2=MKIII）。`getArmorTexture` 与物品图标都按 metadata 分支，这样加新代数只是多一组贴图与一条枚举，不动物品注册。

| 代数 | metadata | 驾驶时噪点 | 表现 |
|---|---|---|---|
| 脑机头盔 MKI | 0 | 重 | 明显雪花 + 偶发横向干扰带 |
| 脑机头盔 MKII | 1 | 轻 | 细颗粒，不影响辨认地形 |
| 脑机头盔 MKIII | 2 | 极轻 | 几乎干净，只在强干扰时闪一下 |

**噪点实现**：客户端全屏覆盖层，不走逐像素绘制（那是纯烧 CPU）。
- 预生成一张 16×16 的灰白噪声贴图，每帧以随机偏移**平铺**整屏，再用档位决定的 alpha 叠加；
- 干扰带是另一条随机水平长条，按档位降低出现频率；
- 强度与频率全部走 `Config`（`noiseMk1` / `noiseMk2` / `noiseMk3`、`glitchChance`），玩家可以关；
- 只在**驾驶中**叠加，退出驾驶立刻消失（与摄像机接管同一生命周期）。

**为什么不按距离加噪点**：距离不影响信号是 R9 的既有结论（控制距离不设上限），把噪点绑到距离上等于偷偷加了个软上限，与设计冲突。噪点是**设备品质**的体现，不是距离的体现。
位置不能由头盔记：头盔不在机器人现场，玩家下线期间机器人可能被推、被撞、被怪打退，头盔那份数据必然过期。所以权威数据放在**机器人自己**这边。

| 载体 | 内容 | 写入者 |
|---|---|---|
| `RobotRegistry`（世界目录下的 **JSON 文件** `<world>/mindrobot/robots.json`） | 机器人 UUID → 频道快照 + 最后上报坐标 + 维度 + 上报时间 | **机器人本体**：每 20 tick 上报一次、跨区块立即上报、销毁时注销、断开时补报 |
| 机器人实体 NBT | 自身位置（世界存档本来就记录，无需额外字段） | 原版存档流程 |
| 头盔 NBT | `lastX/lastY/lastZ/lastDim` | 服务端在接入/断开时从登记表**拷贝**过来，只供 tooltip 显示 |

重连流程改为：
1. 头盔频道 → 查 `RobotRegistry` 里同维度的记录；
2. 有记录 → `RobotChunkLoader.forceAt(记录坐标)`，挂 60 tick 重试；
3. 区块加载、实体回到 `loadedEntityList` → 走 D5 五级校验 → 接入；
4. 全程没有再读头盔里的坐标。

为什么必须落成世界级文件：区块没加载时实体根本不在内存里，问不到它；只有写在磁盘上的世界级数据能在不加载区块的前提下被读到。

为什么用 **JSON** 而不是 NBT：`MapStorage` 的 `.dat` 是二进制 NBT，服主改密码得用 NBT 编辑器；JSON 用记事本就能改、能 diff、能进版本管理。代价是自己管文件的读写与原子性（写临时文件再改名），但这份数据很小、写入点很少，代价可控。落盘时机：标脏后每 200 tick 稀释写入一次，外加世界保存与服务器停止时强制 flush。

### D13 · 头盔的单格容器（R32）
1.7.10 没有"物品自带容器"这种东西，标准做法是借用 GUI 系统：

- `ItemRemoteHelmet.onItemRightClick` 在**潜行**分支里调 `player.openGui(mod, GUI_ID, world, armorSlotOrHandSlot, 0, 0)`；
- 服务端 `IGuiHandler` 返回一个 `Container`，它持有"玩家 + 槽位索引"，自己解析出对应的 `ItemStack`（**不依赖 TileEntity**）；
- 容器里只有一个 `Slot`，`isItemValid()` 只对 `ItemFrequencyChip` 返回 true，其它物品塞不进去，也就不会出现"头盔里装了块钻石"的怪状态；
- 槽位内容变化或容器关闭时，把芯片的频道快照写进头盔 NBT（沿用现有的 `ItemRemoteHelmet.setChannelData`）；
- `onContainerClosed` 里要**顺手把写回做一次**，因为玩家可能直接按 Esc 关掉。

这样芯片的安装动作从"捧着芯片去点头盔"变成"打开头盔插槽"，与 R32 的字面一致，也顺手给以后"取回芯片"留了位置（右键取出即可）。

### D15 · 机器人容器（R35–R37）
| 项 | 做法 |
|---|---|
| 存储 | `EntityRobot` 持有一个 `IInventory`（65 格：9 工具栏 + 54 背包 + 芯片 + 电池），整体存进实体 NBT；实体被摧毁时按正常掉落逻辑处理（部件与内容物分开掉） |
| 打开 | 右键实体 → `openGui(mod, GUI_ID, world, entityId, 0, 0)`，服务端按 entityId 找回实体；**驾驶中不允许打开自己的机器人容器**（与 R10 同源），但别的玩家戴同频道头盔时可以打开未在驾驶的那台 |
| 槽位 | 三个槽位类：`ToolSlot`（9）、`BackpackSlot`（54）、`ChipSlot`（1，只收 `ItemFrequencyChip`）、`BatterySlot`（1，只收 `IElectricItem`）；工具栏与背包的 `isItemValid` 对芯片与电池返回 false |
| 自动拾取 | 在机器人 tick 里按 AABB 吸附附近物品实体，先背包后工具栏；**永不**尝试芯片/电池槽 |
| 界面 | `GuiContainer` 高度按 65 格排布（工具栏一行 + 6 行背包 + 右侧两个特殊槽 + 玩家背包），布局复用现有 `GuiBrainHelmet` 的 drawRect 风格，不引新贴图 |

**为什么把工具栏放在容器第一行**：驾驶时玩家看不到自己的物品栏（R10），机器人网格里的第一行就是他在车上的快捷栏，位置固定、肌肉记忆一致。

### D16 · GT5U 依赖（R38）
- 坐标已核实：`com.github.GTNewHorizons:GT5-Unofficial`（GTNH maven 已在 `settings.gradle.kts` 的 pluginManagement/仓库中配置），当前 release `5.09.55.0`，用 `:dev` classifier。
- `dependencies.gradle` 加 `compileOnly "com.github.GTNewHorizons:GT5-Unofficial:5.09.55.0:dev"`，**不进产物**。
- 电池判定不直接引用 GT5U 具体类，而用 IC2 的 `ic2.api.item.IElectricItem`（GT5U 电池都实现该接口，这也是 GT 机器电池槽的通行契约）；这样 GT5U 内部类重构不会打断我们。
- `@Mod(dependencies = "required-after:gregtech")`：GT5U 是前置，缺失时模组直接拒绝加载比半残运行更好。

### D14 · 装配台与部件（R14/R33/R34）
| 项 | 做法 |
|---|---|
| 方块 | `BlockRobotAssembler` + `TileEntityRobotAssembler`；右键开 GUI |
| 槽位 | 6 个**类型化**槽位：左臂 / 右臂 / 左腿 / 右腿 / 核心 / 摄像头。`Slot.isItemValid` 只接受对应类型（摄像头槽额外接受热成像），塞错位置直接弹回 |
| 部件 | 每种部件是独立物品，携带自身耐久值；部件耐久之和决定成品的结构耐久（R16） |
| 组装 | 六个槽位都正确后点"组装"：在前方生成 `EntityRobot`、清空槽位、把频道数据（来自核心或装配台自带的芯片槽）写进机体 |
| 热成像 | 摄像头槽放热成像时，机体记录 `thermal=true`；驾驶时给驾驶员挂夜视 `PotionEffect`，**退出驾驶立即移除**，绝不留永久 buff |

**为什么用类型化槽位而不是合成表**：部件有六个、还要各自带耐久与可替换的摄像头，合成表表达不了"耐久汇总"和"摄像头可选"。槽位化还能顺手把"装错了想拿出来"变成普通的取放。

|---|---|---|

## 5. 已排除的方案

- **本体无敌**：违背 R6/R7 的设计张力，不做。
- **客户端直接改机器人坐标**：可被伪造，不做（见 D2）。
- **每个功能单独做界面**：违背 R3，全部挂转轮面板。
- **多头盔同时控制一台机器人**：R13 规定同一时刻只有一个驾驶员，公共频道也按"已被占用"拒绝。
- **把耐久做成 `EntityLivingBase` 的 health**：会被血魔法类模组当材料榨取，也会让读血量的模组把它判定成异常实体，已排除（见 D7）。
- **依赖原版目标 AI 自动打机器人**：原版只针对玩家，不注入就永远不会被怪主动打（见 D8）。
